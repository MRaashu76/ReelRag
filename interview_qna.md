# ReelRag: Technical Interview Q&A

This document contains a script of common technical questions an interviewer or senior developer might ask about the **ReelRag** architecture, along with strong, developer-focused answers.

---

## 1. System Architecture & RAG Pipeline

**Q: Why did you choose LangGraph over standard LangChain chains for the RAG pipeline?**
**A:** Standard LangChain chains (like `RetrievalQA`) are linear and hard to control when you need conditional logic or multi-step reasoning. I chose LangGraph because it models the RAG pipeline as a state machine. This allows us to easily implement cyclical logic—like re-querying the database if the first retrieval yields poor context—and makes managing conversational memory and state transitions much more predictable.

**Q: How do you handle real-time streaming to the frontend? Why SSE over WebSockets?**
**A:** We use Server-Sent Events (SSE) from FastAPI to stream the LLM tokens as they are generated by Groq. I chose SSE over WebSockets because our communication is largely unidirectional (client sends a prompt, server streams the response). SSE is much simpler to implement, works natively over HTTP/1.1 and HTTP/2, and doesn't require maintaining persistent two-way socket connections, which reduces backend overhead.

**Q: Can you explain how your chunking strategy works before inserting into the Vector Database?**
**A:** We use the `RecursiveCharacterTextSplitter`. Transcripts are split into chunks of 800 characters with an overlap of 150 characters. The overlap is critical because it prevents sentences or thoughts from being abruptly cut in half, ensuring the LLM receives complete context during the retrieval phase. We then embed these chunks using the local `BAAI/bge-small-en-v1.5` model.

## 2. Scraping & Data Extraction

**Q: Instagram is notoriously difficult to scrape. How did you bypass their login walls and rate limits?**
**A:** Initially, we used `yt-dlp` to extract metadata directly from the page, but Instagram severely rate-limits IPs and hides key metrics (like views and follower counts) behind dynamic JavaScript payloads. To solve this, I integrated a third-party fallback via **RapidAPI** (specifically `instagram-scraper-stable-api`). This acts as a proxy, providing a clean JSON response with the exact engagement metrics without risking our server's IP being blacklisted.

**Q: What happens if a video has no captions available on YouTube or Instagram?**
**A:** We have a robust fallback mechanism. If `youtube-transcript-api` fails to find native captions, the backend automatically downloads the raw audio using `yt-dlp` and passes it through a local OpenAI `Whisper` model to generate the transcript on the fly.

## 3. Frontend Development

**Q: How does the frontend handle the streaming chunks coming from the backend?**
**A:** The Next.js frontend uses a custom `useChat` React hook that consumes the SSE stream via the native `EventSource` or streaming `fetch` API. As chunks arrive, they are concatenated into a state variable. We built a custom parser to detect source citations in the stream (e.g., `[Video A | Chunk 2]`) and dynamically replace them with interactive UI badges using `ReactMarkdown`.

**Q: Why did you use Next.js 15 and Tailwind CSS?**
**A:** Next.js 15 provides excellent support for React Server Components and API routing, which makes the app incredibly fast. Tailwind CSS was used to build a highly responsive, custom design system (like our dark editorial theme) rapidly without managing bloated external CSS files or UI libraries.

## 4. Scalability & Performance

**Q: Your current setup uses local ChromaDB and JSON files. How would you scale this to handle 10,000 creators a day?**
**A:** 
1. **Vector DB:** I would migrate from ChromaDB to **PostgreSQL with pgvector**. `pgvector` scales horizontally, handles concurrent writes much better, and allows for hybrid search (filtering by metadata via SQL + vector similarity).
2. **Background Jobs:** I would replace FastAPI `BackgroundTasks` with a message broker like **Redis + Celery** or **AWS SQS**. This allows us to scale out Whisper transcription workers across multiple GPU instances.
3. **Caching:** I would implement a Redis caching layer to cache metadata responses and identical RAG queries to save on LLM token costs.

**Q: Why use the Groq API instead of standard OpenAI GPT-4?**
**A:** Groq utilizes LPUs (Language Processing Units) which provide insanely fast inference speeds (often >500 tokens per second). For a chat interface where latency is the most critical factor for User Experience, Groq delivers a much snappier, real-time feel compared to traditional API providers.
